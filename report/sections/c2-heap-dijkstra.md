# C2 — Heap / Priority Queue & Dijkstra

**Owner:** Nutsua Bless Yesutor (Pod C Lead)

## What it does

The heap (`gsoo.structures.c2_heap.Heap<T>`) is a binary min-heap over
(element, priority) pairs on a plain `Object[]` that doubles in capacity — no
`java.util.PriorityQueue`. The minimum sits at index 0 (every node ≤ its
children), so `insert` and `extractMin` are O(log n), `peekMin` is O(1), and
`decreaseKey` is O(n) (linear scan to find the element, then O(log n)
re-heapify). That trade is deliberate: the real workloads here are 50-node
graphs and 300-request queues, so the index bookkeeping a Fibonacci or indexed
heap would need buys nothing. In the system it is the dispatch queue's spine —
the "which request next" answer for a shift — and Dijkstra's frontier.

Dijkstra (`gsoo.algorithms.c2_dijkstra.Dijkstra`) answers the routing question:
what is the fastest route between two locations under weighted, degraded roads?
It consumes the frozen `Graph` interface (C4/C5) and the heap (this slot). Edge
weight comes from `Config.effectiveEdgeCost(travelTimeSecs, roadConditionWeight)`
— travel time degraded by the road-condition multiplier, plus the
index-derived `ROUTE_PENALTY` (with `S = 536` it is **2.6**) on flood-prone
roads (weight ≥ `Config.FLOOD_PRONE_WEIGHT_THRESHOLD` = 1.5). The heap holds
node indices keyed by current best distance; a `decreaseKey` lowers a distance
whenever a better path appears, and lazy deletion (a `finalized[]` skip on a
stale extract) keeps the implementation simple.

## Complexity

| Structure/Algorithm | Best | Average | Worst |
|---|---|---|---|
| `Heap.insert` | O(1) (appended, sifts up zero levels) | O(log n) | O(log n) |
| `Heap.extractMin` / `peekMin` | O(1) | O(log n) | O(log n) |
| `Heap.decreaseKey` | O(1) (root) | O(n) (linear locate) | O(n) |
| `Dijkstra` (with this heap) | O(E + V log V) on a sparse graph | — | O((V + E) log V) with indexed decrease-key; our O(n) locate makes the practical constant worse |

The theoretical bound assumes an indexed heap. This implementation's linear-scan
`decreaseKey` makes each relaxation O(n) to locate the node, so the honest
worst case is O(V·E) in the dense limit — acceptable at 50 nodes, and it is the
reason the efficiency lab (B5) should measure heap dispatch and Dijkstra as
separate experiments.

## Tests and why

`HeapTest` (11 tests) and `DijkstraTest` (10 tests):

- **Normal** — ascending-priority extraction, `decreaseKey` promotion,
  multi-hop shortest distances (A→C via B is 3, not the direct 5), path
  reconstruction, and a flood-penalty test asserting a flood-prone edge costs
  `nominal × ROUTE_PENALTY` and can flip which route wins.
- **Boundary** — single-element heap lifecycle, growth across 100 inserts with
  nothing lost or mis-ordered, duplicate priorities, a single-node graph
  (source = target), and a two-node single-edge graph.
- **Invalid** — extract/peek on empty throws `HeapEmptyException`; null element
  and NaN priority rejected on insert; zero/negative capacity rejected;
  Dijkstra on null/empty graphs and unknown source nodes throws; a disconnected
  node reports infinite distance and an empty path.

## One thing it handles badly

Dijkstra assumes non-negative edge weights, and nothing enforces it. A negative
edge silently produces garbage distances (the settled-node guarantee breaks),
so this system must never feed it a negative travel time — the schema doesn't,
and `effectiveEdgeCost` multiplies two non-negative values, but the class
itself does not check. Second weakness: the O(n) linear-scan `decreaseKey`
means the heap's practical constant degrades on large datasets; at 300 requests
it is fine, at a million it would need an indexed heap.
