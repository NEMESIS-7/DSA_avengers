# A1 — Dynamic Array & Binary Search

**Owner:** Fenuku Reynolds Elikem (Architect & Integrator)

## What it does

The dynamic array (`gsoo.structures.a1_dynamic_array.DynamicArray<T>`) is the project's
reference array-backed list: a plain `Object[]` that doubles in capacity whenever it fills up,
giving `add()` amortised O(1) cost without ever using `java.util.ArrayList`. In this system it
holds the loaded request table — the in-memory working set the rest of the app operates on
once the database load finishes.

Binary search (`gsoo.algorithms.a1_binary_search.BinarySearch<T>`) answers one specific
question fast: given a request ID, find its position in that table without scanning every
entry. It's the paired algorithm for A1 because the array *is* the structure binary search
needs — contiguous, indexable, and (this is the precondition that matters) sorted.

## Complexity

| Structure/Algorithm | Best | Average | Worst |
|---|---|---|---|
| `DynamicArray.add()` | O(1) | O(1) amortised | O(n) (on a resize) |
| `DynamicArray.get()` / `set()` | O(1) | O(1) | O(1) |
| `DynamicArray.removeAt()` | O(1) (removing the last element) | O(n) | O(n) (removing index 0 shifts everything) |
| `binarySearch()` | O(1) (target is the first `mid` checked) | O(log n) | O(log n) |

Binary search's precondition is the whole story: it only works on a sorted array. Run it on
unsorted input and there's no guarantee it finds anything, or even that it behaves — see
counterexample (pending, evidence ledger item, not yet written up).

## Tests and why

`DynamicArrayTest` (9 tests) and `BinarySearchTest` (5 tests):

- **Normal** — resize behaviour across many adds (`verifyResize`), a mid-array `removeAt`, and a
  present-value search landing mid-array. Confirms the core contract under ordinary use.
- **Boundary** — first/last element search, a single-element array, and zero-initial-capacity
  construction followed immediately by `add()`. The last one caught a real bug (below).
- **Invalid** — negative capacity, out-of-bounds `get`/`set`/`removeAt`, searching a target not
  present, and searching an empty range. These are the cases where "it works on my machine"
  most often hides a crash.

## Two bugs these tests/traces caught

1. **`binarySearch()`'s recursive branches were swapped** — when `arr[mid] > target` it recursed
   into the *right* half instead of the left, and vice versa. Against the real dataset this
   doesn't converge: `left`/`right` collapse to `(0, -1)` and every subsequent call recomputes
   `mid = 0`, so it recurses forever. Caught as a `StackOverflowError` on the very first test
   run, not a subtle logic error — fixed by correcting the branch directions and adding the
   missing `left > right` base case.
2. **`DynamicArray.grow()` didn't grow from zero capacity** — `data.length * 2` when
   `data.length == 0` is still `0`, so `new DynamicArray<>(0)` followed by one `add()` threw
   `ArrayIndexOutOfBoundsException`. Not caught by the original boundary test, since it
   constructed a zero-capacity array but never called `add()` on it. Fixed by special-casing the
   zero-length case to grow to 1.

## One thing it handles badly

Binary search's precondition — the array must already be sorted — is silent. Nothing in
`BinarySearch` checks it or complains if it's violated; it just returns a wrong-but-plausible
answer, or fails to find something that's actually there. That's precisely the argument for the
"binary search on unsorted input" counterexample this slot owes the evidence ledger (not yet
written). It's also why `DynamicArray` itself deliberately does *not* try to keep itself sorted —
that responsibility belongs one layer up, with whichever sort (quicksort, merge sort) populates
it, keeping each structure honest about what it actually guarantees.
