## What it does

The B5 Map (`gsoo.structures.b5_map.CustomMap<K,V>`) is a custom key-value store built
without `java.util.Map`, `HashMap`, or `TreeMap`. It's backed by two parallel `Object[]`
arrays — one for keys, one for values, at matching indices — that double in capacity
whenever they fill up, the same growth strategy A1's `DynamicArray` uses.

Unlike B4's hash table, this Map deliberately does not hash. Lookups scan linearly through
the key array until a match is found or the array is exhausted. That's a design choice, not
an oversight: the project already has a hashed key-value structure in B4, so B5 exists as the
plain-array baseline the efficiency lab can measure a hashed structure against.

In the running system, `CustomMap` is used to hold resource records keyed by `resource_id`
— for example, looking up a resource's capacity or current availability without scanning the
full `resources` table each time.

The **algorithm** half of this slot differs from most others: rather than a paired
search/sort/graph algorithm, B5 owns the empirical **efficiency analysis** work — running
and interpreting all 6 required performance experiments (search comparison, sort comparison,
hash load factor, BST vs balanced tree, heap dispatch, graph runtime) once the other slots'
structures are complete. That work is scheduled for Week 3 per the milestone timeline and is
not yet started; this section covers the Map structure itself.

## Complexity

| Operation | Best | Average | Worst |
|---|---|---|---|
| `put()` (new key) | O(1) amortised | O(n) (must scan to confirm key is new) | O(n), plus O(n) on a resize |
| `put()` (existing key) | O(1) (key at index 0) | O(n) | O(n) (key at last index) |
| `get()` / `containsKey()` | O(1) | O(n) | O(n) (key absent — scans everything) |
| `remove()` | O(1) | O(n) | O(n) (removing index 0 shifts every element after it) |

The average and worst cases are dominated by the linear key scan (`indexOf()`), which every
public method routes through. This is the direct trade-off of avoiding a hash function.

## Tests and why

`CustomMapTest` (3 tests, matching the Definition of Done requirement):

- **Normal** — put/get/remove/update sequence on a small map, confirming that updating an
  existing key overwrites its value and returns the old one without changing `size()`.
- **Boundary** — behaviour on an empty map (`get`/`remove`/`containsKey` all safely return
  null/false rather than throwing), plus inserting 20 entries to force multiple resizes past
  the default capacity of 8, confirming no data is lost or corrupted across a resize.
- **Invalid** — a null key throws `IllegalArgumentException` on every public entry point
  (`put`, `get`, `remove`, `containsKey`).

## A bug this testing caught

While re-running the trace demo to switch it from placeholder data to the real dataset,
`keySet()` threw a `ClassCastException`: `class [Ljava.lang.Object; cannot be cast to class
[Ljava.lang.String;`. The original implementation tried to return a generic `K[]` by casting
`new Object[size]` directly — which fails at runtime because Java can't create a real
generic array; the cast only appears to type-check at compile time via
`@SuppressWarnings("unchecked")`.

Fixed by having `keySet()` return `Object[]` honestly instead of pretending it's `K[]`, and
casting each element individually at the call site (`MapTraceDemo`) where the actual runtime
type is known. This is caught by actually *running* the trace against real data, not by the
unit tests, since the tests never called `keySet()` — worth noting as a gap to close: a
fourth test covering `keySet()` output directly would have caught this earlier.

## One thing it handles badly

Every operation degrades to O(n) as the map grows, because lookups are a linear scan rather
than a hash. With 30 resources this is invisible; at the scale the hash-load-factor
experiment tests (100–20,000 keys), the gap between this structure and B4's hash table
should be dramatic — that comparison is exactly what the Week 3 efficiency lab is for.
