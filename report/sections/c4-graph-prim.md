
# C4 — Graph (Adjacency List) & Prim's Algorithm

**Owner:** Botwe Michael

## What it does

The graph (`gsoo.structures.c4_graph_adjacency_list.AdjacencyListGraph`) is one of two
implementations of the shared `Graph` interface (the other, `c5_graph_adjacency_matrix`,
owned by C5) -- both representing the same domain: the district's external health network
(communities, CHPS compounds, health centres) joined to the internal hospital corridor
network at a single gateway node. Internally it's a self-managed array of node entries,
each holding its own self-managed array of edges -- no `java.util.List`/`ArrayList`/`HashMap`
anywhere in the core structure, per the assignment's built-in restriction.

Prim's algorithm (`gsoo.algorithms.c4_prim.PrimMST`) is the paired algorithm: given a start
node, it grows a minimum spanning tree by repeatedly picking the cheapest edge that connects
the current tree to a new node. In this system it answers the question "which roads/corridors
are the minimum set needed to keep the whole network connected, at minimum total cost?"

A key design decision, worked out with A1 while freezing the shared interface: the graph
exposes two different neighbor-lookup methods, not one. `getNeighbors()` respects one-way
roads (used by Dijkstra, DFS, BFS -- anything answering "where can I legally travel from
here?"). `getConnections()` ignores direction entirely (used by Prim and Kruskal, since MST
is mathematically undefined on directed graphs -- a spanning tree is about connectivity,
not legal direction of travel).

## Complexity

| Structure/Algorithm | Best | Average | Worst |
|---|---|---|---|
| `addNode()` | O(n) (duplicate check scans) | O(n) | O(n) |
| `addEdge()` | O(n) (duplicate + node lookup) | O(n) | O(n) |
| `getNeighbors()` / `getConnections()` | O(1) (isolated node) | O(deg(v)) | O(deg(v)) |
| `getAllEdges()` | O(V + E) | O(V + E) | O(V + E) |
| `PrimMST.run()` | O(V^2) | O(V^2) | O(V^2) |

Node lookup throughout is a linear scan over the node array (`findNodeIndex`), since
`HashMap` isn't allowed for the core structure -- an honest O(n) tradeoff, discussed with
the team, that could be improved by reusing B4's hash table in a later pass. Prim's O(V^2)
comes from scanning every in-tree node's connections on every iteration to find the next
cheapest edge, rather than using a priority queue (C2's heap slot) -- a simpler, array-based
approach in the same spirit as selection sort's repeated linear scan for the minimum.

## Trace walkthrough

Full trace evidence, generated by actually running the code -- both a small hand-worked
6-node example (to verify the mechanism) and the full real 50-location, 100-road dataset
loaded from a local Postgres database via `Session.load()`:
[`docs/evidence/c4-trace-tables.md`](../../docs/evidence/c4-trace-tables.md).

On the real dataset: 100 road rows loaded to 98 unique edges (2 duplicates in the seed data
correctly rejected by `hasEdge()`), Prim's from `EXT-C01` reaches all 50 nodes with 49 edges,
total cost 16750.40. Notably the single most expensive edge in the tree, `GATE-01-EXT-R01`
(cost 2700.00), is still included -- it's the only road connecting the regional referral
hospital to the network, so despite its cost there's no cheaper way to keep it connected.

## Tests and why

`AdjacencyListGraphTest` (3 tests) and `PrimMSTTest` (3 tests):

- **Normal** -- a small graph mixing directed and undirected edges, confirming
  `getNeighbors()` correctly excludes an illegal reverse move on a one-way edge while
  `getConnections()` still reports it; and Prim's on the same hand-worked 6-node graph
  used in the trace evidence, checked against the known-correct cost and edge count.
- **Boundary** -- an isolated node with zero edges (both neighbor methods must return
  empty, not null, arrays); and a disconnected graph for Prim's, checking it reports
  `connected = false` with a partial tree rather than crashing or lying about reaching
  everything -- directly relevant to the domain, since a closed/flooded road could
  genuinely split the real network.
- **Invalid** -- duplicate node id, an edge referencing a node that doesn't exist, querying
  neighbors of an unknown node, and running Prim's from an unknown start node. All throw
  `IllegalArgumentException` rather than failing silently.

## One bug integration with the real database caught

The `Graph`/`Edge` interface originally had no way to represent a closed road at all --
built and frozen before any real data existed. Once `Session.java`'s real database loader
was wired up, it became clear the `roads` table has a genuine `is_closed` column with real
closed roads in the dataset, and there was nowhere to put that information once loaded. Not
a crash, but a silent data-loss bug: every closed road would have loaded as if it were open,
and no downstream algorithm could ever have known to treat it differently -- directly
undermining one of the system's required questions ("what's reachable if a road is
closed?"). Fixed by adding an `isClosed` field to `Edge` and threading it through
`addEdge()`, `AdjacencyListGraph`, and the real loader in `Session.java`, which now reads
`road.isClosed` straight from the database row. The graph itself still doesn't filter closed
roads out automatically -- that's left to whichever traversal (BFS/DFS reachability) needs
to decide whether to skip them, keeping the graph an honest, unopinionated container of
what physically exists.

## One thing it handles badly

`PrimMST`'s edge-cost calculation (`travelTimeSecs * roadConditionWeight`) is currently
duplicated locally rather than calling `gsoo.app.Config`, since `Config` doesn't yet expose
that formula project-wide -- flagged as a `TODO` in the code. This is exactly the kind of
duplication the brief's "defined once, in Config, never recomputed differently elsewhere"
rule exists to prevent, and should be fixed once `Config` has the formula.
