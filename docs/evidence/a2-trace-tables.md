# A2 Trace Tables — Linked List & Linear Search

Generated by running `gsoo.algorithms.a2_linear_search.LinearSearchTraceDemo`, which loads
the 300 real `REQ-000x` request IDs from `sql/seed/service_requests_seed.sql` into the A2
`LinkedList` (no live DB required, so this is reproducible from a clean checkout), pulls them
out via the linked list's own iterator into a plain array, and runs
`LinearSearch.searchWithTrace()`. The numbers below are copied directly from that run.

```
mvn exec:java -Dexec.mainClass=gsoo.algorithms.a2_linear_search.LinearSearchTraceDemo
```

Deliberately searches the **same two targets** `BinarySearchTraceDemo` (A1) uses —
`REQ-0187` (present) and `REQ-9999` (absent) — against the same 300-entry dataset. That's what
makes the "linear vs binary search" comparison (evidence ledger, owned jointly by A1 and A2) a
fair one: identical input, identical target, only the algorithm differs.

Dataset loaded: 300 request IDs, `REQ-0001` .. `REQ-0300` (0-indexed array, indices 0–299).

## Table 1 — Present target: `REQ-0187`

| Step | Index | `arr[index]` | Comparison | Action |
|------|-------|--------------|------------|--------|
| 1–186 | 0–185 | `REQ-0001` .. `REQ-0186` | not equal | continue to next index |
| 187 | 186 | `REQ-0187` | equal | match — return index **186** |

**Result:** `search(..., "REQ-0187") = 186` — **187 comparisons**, checking every element up to
and including the match, since linear search has no way to skip ahead. Contrast with A1's
binary search on the identical target: **3 comparisons** (`docs/evidence/a1-trace-tables.md`).

## Table 2 — Absent target: `REQ-9999`

| Step | Index | Comparison | Action |
|------|-------|------------|--------|
| 1–300 | 0–299 | not equal (all 300 real IDs checked) | continue, then reach end of array |
| — | — | — | array exhausted — return **-1** |

**Result:** `search(..., "REQ-9999") = -1` — **300 comparisons**, the actual worst case for
n = 300 (every real ID gets checked, since the target doesn't exist). Contrast with A1's binary
search on the identical target: **9 comparisons** (⌈log₂ 300⌉). This is the concrete number
behind "linear search is O(n), binary search is O(log n)" — not asserted, measured on the same
real 300-row dataset both slots share.

## Why this comparison is fair

Both traces use the exact same 300 real request IDs, loaded from the same committed seed file,
searched for the exact same two targets. The only variable is the algorithm — linear search has
no ordering precondition and must potentially check every element; binary search requires the
array to be sorted (true here — the IDs are naturally ascending) and exploits that with each
comparison eliminating half the remaining range. The 187-vs-3 and 300-vs-9 comparison counts
above are what that difference actually costs on real data, not a theoretical claim.
