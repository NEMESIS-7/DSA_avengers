- Connected quicksort into the main console app chapter for sorting urgency values.
- Added documentation evidence for BST insertion/in-order behavior and quicksort partition behavior using committed project seed data.

**What broke or was missing:**

- The BST currently stores only `int` values, so project fields such as request IDs and deadline timestamps must be converted into integer keys before they can be inserted.
- The quicksort implementation sorts plain `int[]` values, so it can sort urgency scores but does not keep the full service-request record attached to the score.
- Because the live database was not available while documenting, the trace uses the committed seed dataset in `sql/seed/service_requests_seed.sql`. This keeps the evidence reproducible from the repository.
- Quicksort is not stable, so if two requests have the same urgency, their original arrival order is not guaranteed by this implementation.

**Decided:**

- Keep the BST implementation simple and focused on the assessed integer tree operations.
- Use in-order traversal as the evidence that the BST preserves sorted order.
- Use pending service requests from the project seed file as the trace dataset.
- For the BST trace, convert each selected request deadline into a sortable integer key using `MMDDHHMM`, because all selected seed records are from July 2026 and the current BST accepts integers only.
- For the quicksort trace, sort the urgency values from the same selected pending requests.
- Document the adapter limitation instead of pretending the current BST stores full request objects.
