# A4 Trace Table — Queue-Driven BFS

Generated by running `gsoo.algorithms.a4_bfs.BFSTraceDemo`, which loads all 50 real
locations and roads straight out of the committed seed data (`sql/seed/locations_seed.sql`,
`sql/seed/roads_seed.sql` — no live DB needed, so this is reproducible from a clean
checkout), builds the graph via `AdjacencyListGraph`, and runs BFS (instrumented to print
each step) from `GATE-01`. The table below is copied directly from that run, not typed by
hand.

```
mvn exec:java -Dexec.mainClass=gsoo.algorithms.a4_bfs.BFSTraceDemo
```

Dataset loaded: 50 locations, 100 roads in the seed file — but 2 are duplicate pairs
(`R-035` repeats `R-010`'s `EXT-H02`↔`GATE-01`; `R-098` repeats `R-046`'s `INT-14`↔`INT-08`).
`AdjacencyListGraph.addEdge()` rejects duplicate edges by design, so the loader skips and
logs both rather than crashing. **98 roads actually load.** This is a real seed-data issue,
flagged to A3 separately — not a bug in BFS or the loader.

The frontier queue here is this slot's own `DynamicQueue` — BFS needs strict FIFO order to
guarantee it visits nodes in non-decreasing distance from the source, level by level, which
is the whole reason this queue and this algorithm are paired in the same slot.
