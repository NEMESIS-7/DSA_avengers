# Starting Your Slot — A One-Page Guide

Give this to every member. It assumes names are already assigned to slot IDs (see `README.md` §4).

---

## 1. Find yourself

Look up your **Slot ID** (e.g. `C2`) in the README or the Notion Slot Board. That row is your data structure, your algorithm, and — if you have one — your spine role.

## 2. Clone and branch

```bash
git clone <repo-url>
cd repo
git checkout develop
git pull
git checkout -b feature/<slot-id>-<short-name>
```

Example: `git checkout -b feature/c2-heap-dijkstra`

Slug format: lowercase slot ID, dash, 2–3 word description. No spaces.

## 3. Where your code goes

```
src/main/java/gsoo/structures/<your-slot-folder>/    ← your data structure
src/main/java/gsoo/algorithms/<your-slot-folder>/    ← your algorithm
src/test/java/gsoo/structures/<your-slot-folder>/    ← your tests
src/test/java/gsoo/algorithms/<your-slot-folder>/
```

Folder names already exist in the repo, matching your slot (e.g. `c2_heap`, `c2_dijkstra`). Don't create new top-level folders — if you think you need one, ask the Architect (A1) first, since it likely means an interface question.

## 4. Before you write a line of implementation

Check whether your structure or algorithm's interface has been frozen yet (Week 1 priority — graph and heap first, since 5 other slots depend on them). If it hasn't, don't guess at the signature; ask A1. Guessing wrong here is the single most expensive mistake in this project, because everyone downstream inherits it.

## 5. Definition of Done — what "finished" means

Not just "it compiles." All five, every time:

- [ ] Implementation matches the frozen interface, no banned built-ins (`HashMap`, `TreeMap`, `PriorityQueue`, `Stack`, `ArrayDeque`, etc.)
- [ ] Three tests: normal case, boundary case, invalid input
- [ ] Trace output generated by your own code from the real dataset — not hand-written afterward
- [ ] Report section drafted into the shared skeleton
- [ ] Dev-log entry: what you did, what broke, what you decided

Your pod lead checks this list before approving your PR. Missing any item gets "changes requested," not a merge.

## 6. Commit as you go

Small, frequent commits beat one giant diff the night before a deadline — your pod lead can actually review small commits.

```bash
git add .
git commit -m "C2: heap insert/extractMin implemented, boundary tests added"
git push -u origin feature/c2-heap-dijkstra
```

## 7. Open your PR into `develop`

Not into `main`. Tag your pod lead as reviewer. Include in the PR description:

- Which Definition of Done items are checked
- Anything you're unsure about (better flagged now than at the oral defense)

Your pod lead reviews and merges. You delete your branch after merge.

## 8. If you get stuck for more than 48 hours past a checkpoint

Say so — in the pod standup, not silently. Your named backup starts reading your code at that point by design (see README §4). You still defend your slot at the oral panel regardless of who ends up writing it, so speaking up early is entirely in your own interest.

## 9. Update the Notion Slot Board

Move your card's status as you go: **Not started → In progress → In review → Done**. Check the four checkbox fields (Tests / Trace / Report Section / Dev Log) as you complete them — that board is how the Architect and pod leads see status without asking.

---

Questions about your interface, your pairing (why your structure and algorithm go together), or the domain model → see `README.md`. Questions about git workflow → see `CONTRIBUTING.md`. Anything not answered by either → ask your pod lead first, then the Architect.
